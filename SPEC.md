# agent-app spec

A local desktop workspace with a read-only viewer for notes, gate status, diffs and images. MIT licence. Product name: agentVIEW; internal packages and configuration retain the `agent-app` name.

## Foundation workspace (2026-11-21)
The default window presents two simulated provider intake agents (Claude and Codex), project coordinators reporting to their intake, and worker/refuter subagents reporting to a coordinator. Hierarchy view shows that chain; project view groups coordinators from both providers. Provider, project and availability filters retain parent context.

The workspace stores its own demo roster, availability and conversations in a private local SQLite database. Messages are persisted before synthetic delivery; busy/paused recipients remain queued. Delivery and one simulated reply commit atomically, with idempotent send requests and bounded history pages (100 rows per query, at most 1000 recent rows displayed). Restart preserves history and availability. The simulated roster launches or attaches to nothing and Zellij sessions are untouched. (Real sessions are a separate page; see Live sessions below.)

Workspace commands are allowed only in the workspace window at its exact origin. They cannot choose arbitrary paths, senders, processes or hierarchy assignments. The separate document window has no workspace capabilities. Token usage is grouped by agent/provider but marked unavailable until real adapters supply telemetry; no tokenizer estimate substitutes for measurement. Jobs and instruction editing remain later milestones.

## Rules the app keeps
- Writes into a person's project folders happen only through the consent-gated "Save into a project" dialog (see "Writing into a project folder" below): a fixed set of the app's own documents, a registered session's folder, a preview, a two-step confirm and an optional backup first. Nothing else the app does writes outside its own data folder.
- It never grants an approval. An approvals view shows what a person must decide and where they decide it.
- Credentials: the app shows names and where a secret lives, never the value, in the UI, logs or repo. In the viewer this is enforced by deny rules on file names plus a best-effort redaction of obvious token shapes in displayed text. Redaction is not a guarantee, so secrets must not sit in allow-listed files.
- Read-only path allow-list. Paths are resolved with realpath (symlinks followed) before the deny rules, then checked against explicitly configured files or directories. An allowed directory includes its descendants subject to deny rules. Keys, credentials and build folders are denied. Hardlinks are refused by both viewers. A diff view never renders a denied file.
- It runs Claude Code or Codex only as the user's own explicitly started sessions with their existing permission modes (the Sessions page). The simulated roster runs nothing.
- No server beyond localhost. Files or SQLite, no database server until a need is shown.
- Synthetic data only in tests and screenshots.

## First milestone: read-only viewer
Views: shared docs, gate status (from a gate log file), recent file changes with diffs, images.
Data sources: files under an explicit allow-list in a config file. Document browsing never writes these files. The separate workspace writes only its own local application database.
Done when: it starts, lists the allow-listed docs, shows a diff of a synthetic file, and a test proves an excluded path is refused.

## Pages added after the first milestone
Sessions (real CLI terminals, Remote Control toggle, stop-all, exit status, remove a registered project with a second confirming click: only the app's own saved record and its usage numbers are deleted, never the project folder or the provider's history, and a running session cannot be removed), Overview (observable data only: no sub-agent or network-bandwidth data), Token usage, Settings (themes, preferences, bundle), Pre-PR review (manual labels, not approvals), Notes and the Claude config view (below). See docs/code-map/README.md.

## Later, not started
Approval views, sandbox settings, subagent activity, agent-to-agent messaging, jobs.

## Image support
The viewer shows images from allow-listed paths. Same realpath, deny and allow-list policy as text; raster types only (png, jpg, gif, webp) checked by file signature, no SVG; served as images with `nosniff` and a CSP that allows only same-origin images; no image from a denied folder. `/img` serves files up to 5 MB, 16384 px a side and 16 megapixels, after a signature, extension and header-size check. Files over the cap are refused, never cut. No decoding, and no metadata (EXIF, text chunks) is read or shown. A doc page shows images referenced by relative markdown links only when they pass the same path policy; http, absolute, `~`, `data:` and denied-folder references are listed as not shown.

## Viewer limits
/view is capped at 1 MB and /gate at 16 MB, each with a visible "Truncated" notice. /diff reads 200 KB per file and prints at most 2000 lines. The gate list is a best-effort text parse and says so on the page; an empty list does not mean nothing is pending. Files are opened without following symlinks and checked against the path that passed the policy.

## Gate log order
The gate parse assumes the log lists rows newest first. A row is closed only by a row above it. If the file is ordered the other way, approved items show as pending.

## Running the viewer (stdlib only, Python 3.11+)
`cp allowlist.example.toml allowlist.toml`, then `python3 viewer/server.py --gate-file <path-to-gate-log>` and open http://127.0.0.1:8765/. Tests: `python3 -I -m unittest discover -s tests`.
After cloning run `git config core.hooksPath .githooks`. The hook can be skipped, so `.github/workflows/ci.yml` runs the same scan (`scripts/scan-files.sh`) on every commit, plus an identity and attribution-line check and the tests.

## Notes library and bundles
The workspace has a Notes page: Markdown pages grouped on shelves, kept in the app's own database (not in repositories or shared documents, so the read-only viewer rule is unchanged). Editor with toolbar, split live preview using the same safe renderer (no HTML, links as text, no images or scripts), search, save history (last 20 versions per page), stale-save refusal, delete with a second confirming click. Limits: 256 KB a page, 2000 pages.

Export and import bundle (Settings): one JSON file holding preferences and the Notes library with a SHA-256 integrity check and a format number. Not included: sessions, terminal content, conversations, usage records, review labels, allow-lists, paths, credentials. Quick-prompt text is part of the preferences and is exported as typed, so do not keep secrets in quick prompts. Bundles are written to and read from the app's private exports folder only (mode 0700, files 0600); the interface passes a listed file name, never a path. Import is check-then-import: pages are only added (a title clash is renamed with " (imported)"), nothing is overwritten or deleted, and preferences are replaced only when the box is ticked, through the normal validated save.

## Git view
A read-only page that shows, for each git repository that contains an allow-listed path: branch, ahead/behind counts against the upstream already known locally, changed and new files, the last 15 commits, and whether those commits use the repository's own configured e-mail. It runs only `git status --porcelain=v2 --branch -z --untracked-files=normal`, `git log -n15` with a fixed format, and `git config --local --get user.name` / `user.email`, each with a fixed argument list, a 5 second limit, 1 MB of output, no pager, no fsmonitor, no hooks path and a cleared environment. The page passes a repository path only to pick one from the listed set. File names matching the deny rules are counted but not listed; commit subjects pass the token redaction. There is no add, commit, fetch, pull, push, checkout, stash or config change, so the view cannot move a repository or contact a remote.

Git safety: `git status` can run a command named by a `filter.<name>.clean` entry in a repository's own config, and an agent working in that folder can write that file. Both git views therefore refuse a repository whose config (including anything it includes) has a `filter.*` or `include` entry, and say so; a unit test checks that a configured filter command does not run. The other git settings that could run commands (fsmonitor, hooks, pager, external diff, the global and system config) are switched off on every call.

## Webhook notifications
A card in Settings stores up to five named webhook destinations. Each destination chooses its events: a running session with no terminal output for 10 minutes ("quiet"), a session that stopped with an error after running in this app session ("error"), or one that finished with exit 0 ("finished"). Defaults are quiet and error. The message names the agent and says it "may be waiting"; the app does not see approvals and never claims one is pending. A background check runs every 30 seconds, reads only the same activity data as the Overview, never blocks terminal actions, and sends each condition once (the quiet condition re-arms after output resumes). At most 20 messages an hour per destination.

Each address is treated as a secret: it is accepted only as `https://` with a public-looking host name (no user info, no IPv6 or private, loopback or link-local addresses, no local names), is kept only in the app's private database, is never returned to the page (only its host name), is not part of export bundles or diagnostics, and is passed to `curl` on standard input, never on a command line. The only subprocess is `curl -q --silent --show-error --proto =https --proto-redir =https --max-redirs 0 --max-time 10 ... --data-binary <message> -K -` with a cleared environment (PATH, locale, certificate and proxy variables only). Names that resolve to a private address are not detected. This is the app's first outbound network use; it is off until an address is saved and notifications are ticked, and the settings page is the only way to change it. Editing a destination keeps its saved address unless a new one is pasted. An earlier single address is migrated as "Default".

Webhook text: a mailbox message (up to 140 characters of it) and a blocked board card (title up to 80 and note up to 100 characters) are agent-written text that goes into the notice the app sends to every enabled webhook destination and, if on, to desktop notices, after the same redaction as everywhere else. Anything an agent writes can therefore leave the machine through a webhook the person turned on. Webhook host names are checked as text, not resolved: a public-looking name that resolves to a private address is not detected.

## Claude hook signal
The only reliable way to know that Claude Code is waiting for a person is Claude Code itself, through its Notification hook (fields `session_id`, `cwd`, `message`, `notification_type`). The Notifications tab in Settings shows a hook snippet that the person pastes into their own `~/.claude/settings.json`; the app never edits Claude's settings. The hook appends one small JSON line (time, session id, folder, notification type, message) to `claude-notify.jsonl` in the app's private `signals` folder (mode 0700). The app only reads that file: symlinks refused, complete lines only, lines older than the app start ignored, fields validated, text stripped of control characters and passed through token redaction. A permission, elicitation or agent-input notification becomes a "waiting for your decision" message and an idle prompt becomes "waiting for your input", sent to destinations that chose the "Claude is waiting" event, once a minute per session and type, naming the registered session for that folder or the folder name (never the path). A signal is data from Claude Code: it never answers a prompt, never approves anything and is not an approval state.

## Claude settings and inventory
The Claude config page has two more read-only tabs. Settings shows permission rules (allow, deny, ask; token shapes redacted), the default permission mode, hooks (event, matcher, type and the program's file name only), environment variable names (never values), the model, enabled plugin names, and which helper commands exist (never their text), from `settings.json` and `settings.local.json` in the Claude config folder. Skills & agents lists skills, commands and agents with name and description (and an agent's model and tools) taken from the first 4 KB of each file; bodies are never returned. Symlinked entries are followed only to plain files whose path passes the deny names. Nothing is written or run.

## Claude memory and session history
Two more read-only tabs on the Claude config page. Memory lists and shows Markdown files from fixed places only: `CLAUDE.md` in the Claude config folder, `projects/<slug>/memory/*.md`, and `CLAUDE.md` / `AGENTS.md` in allow-listed folders. The page passes a key that the app re-resolves against its own listing (no path is ever accepted); each file is resolved with realpath and must pass the deny names, is capped at 64 KB, has control characters stripped and token shapes redacted. History lists past Claude sessions (project folder name, session id, size, modification time) with a copy-able `claude --resume <id>` line; it reads only directory metadata and never opens a conversation file. Nothing is written or run.

## Time per project
Background mode: the Settings choice "When I close the window" is "Stop my sessions and quit" by default. With "Keep running sessions in the background" and at least one session running, closing the window hides it and the app keeps the sessions; a second launch or `agentview --quit` talks to it over a private unix socket (words `show` and `quit` only; details and limits in docs/LIVE-SESSIONS.md). A hidden app exits when its last session ends. No tray icon.

The Overview shows, for each project, how long its sessions ran and how long they were active (terminal output within the last 2 minutes), for today, the last 7 days and all time. The 30-second background check adds the elapsed time to daily totals (UTC days) in the app's own database; a project with several sessions counts once. It only counts while the app is open and measures terminal activity, not time at the keyboard. Totals older than 400 days are dropped, are not part of export bundles, and cannot be edited from the page.

## Layout
The workspace uses a floating rounded sidebar, separate summary tiles with an icon, rounded cards, pill tabs on Settings (General, Data, Notifications, About; they only show or hide blocks) and a "By state" bar list on the Overview. The Overview flow tile draws a small sparkline of the terminal data rate seen since the page was opened. These are presentation only and add no data or commands.

## Polish
Presentation and keyboard only, no new data or commands. Disabled buttons stay readable (dashed outline, muted text) and Sessions shows a one-line reason when Start is disabled. The empty terminal area says what to do. Session tiles lead with a status dot and show the provider as a small chip. Buttons, selects and text inputs share one minimum height and radius, and keyboard focus is always visible. Alt+1 to Alt+9 open the nth sidebar page, Alt+0 opens Settings, and Esc closes the open section or leaves the field; neither works inside a terminal, where those keys belong to the program. Below 1000 px wide the sidebar folds to icons unless the person has chosen to expand or collapse it. Settings, About shows the version and build id (the short commit).

## Flow view
A read-only page drawing you, the providers and the registered sessions as a graph, with one status dot per session: running, quiet for 10 minutes, stopped with an error, or not running. It uses only the activity data of the Overview (no new command). It shows no approval state, no message edges and no sub-agents, because the app cannot observe them.

## Backup with rclone
A card in Settings copies the app's own exports folder (the bundles) to a remote already configured in rclone, into `agentview-backup/exports`. The app runs only `rclone listremotes` and `rclone copy <exports folder> <remote>:agentview-backup/exports --immutable --max-depth 1` (with `--dry-run` for the preview), with a cleared environment apart from PATH, HOME and XDG_CONFIG_HOME, and a time and output limit. `copy` only adds files, so nothing is deleted or overwritten at the destination. The remote must be one that `listremotes` printed; only names are shown, never rclone's settings or raw output. A real copy is accepted only after a dry run for the same remote in the same app session (ten minutes, one copy per dry run) and a second confirming click. Setting up remotes stays in rclone itself.

## Claude config view
A read-only page for `~/.claude.json`: project folders with trust flag, allowed-tool count, history count and MCP server names (kind and command or host name only), plus global MCP servers. Environment values, arguments, headers, tokens, account details and history text are never returned to the page. A server URL is reduced to its host name (no path, query or user info) and a command to its first word's file name. The file is never written, because Claude Code rewrites it while running. Backup, diff and edits are deliberately not offered.

## Needs you, Codex signal and desktop notifications
The Overview's attention card also lists recent signals the background check saw: a session quiet for 10 minutes, a session that ended with an error, and "waiting" lines from the agent hooks (Claude Notification hook, Codex `notify`). They are kept in memory only (30 lines, 6 hours), can be hidden per line in the page, and are data: nothing is answered or approved. Codex's `notify` setting (user-level `~/.codex/config.toml`) runs a program with one JSON argument; the only documented type is `agent-turn-complete`, so a Codex line means "finished its turn and is waiting for your input", never a pending approval. The Settings snippet turns it into a small line in `codex-notify.jsonl` (no reply text) and the app only reads it, with the same rules as the Claude file. Desktop notifications are a second destination: off until switched on (a flag file in the app data folder), one fixed `notify-send` call with a cleared environment (PATH, session bus and display variables only), no address and no network, at most 30 an hour, for quiet, error, waiting and plan-limit events.

## Claude plan limits and resume after a restart
Plan limits: Claude Code gives its status line script the same 5-hour and 7-day plan usage that `/usage` shows (`rate_limits.five_hour` and `.seven_day`: used percentage and reset time; only for Pro, Max and Ultra logins and only after a session's first reply). Settings shows one line for the person to add to their own status line script; it writes `claude-limits.json` in the app's private signals folder. The app only reads that file (symlinks refused, 4 KB cap, percentages checked to be 0 to 100) and never reads Claude credentials or any other Claude file, and calls no server. The Overview shows the last values with their age; they can be out of date. An optional alert percentage (70, 80, 90 or 95; off by default) sends one "plan limit" line per window and reset time to the "Needs you" list, to desktop notifications and to webhook destinations that chose "Plan limit"; data older than 2 hours or windows already reset are ignored.

Resume panel: the Sessions page lists sessions found "interrupted" at start (a crash, reboot or forced close) and says nothing was restarted. Each has a Resume button, and "Resume all" asks for a second click. Resume is the existing Start: the exact saved ID with `claude --resume` or `codex resume` in the session's own folder and permission mode; nothing is ever resent, and nothing starts without that click.

## Quick prompt library
Quick prompts (Settings, "Coordinator quick prompts") hold up to 24 presets; each pastes one line into the selected native prompt and never adds Enter. A built-in library of 13 ready-made prompts (update resume state, handoff Claude to Codex and back, pick up from a handoff, list blockers, run tests and report, review uncommitted changes, what changed, plan first, explain the last failure, check against rules, pause and ask, a short status for the project manager) can be added one at a time; an added prompt is an ordinary preset that can be edited, moved or removed, and one already in the list is not added twice. The library is fixed text in the app; the app writes only the person's own preferences, and presets stay in the preference bundle as typed (no secrets in prompts).
A plan-limit window that is already over the alert percentage when the app starts is marked as known and not alerted again; the Overview still shows it with its age. Windows whose reset time has passed are hidden.

## Resume state and handoff
The Overview shows, for each registered session, which notes files the app can see for its folder (Claude memory files under `projects/<folder>/memory/`, and `CLAUDE.md` or `AGENTS.md` in allow-listed folders) and whether the newest one changed after the session's last activity ("looks current" or "older than the last activity by ..."). It reads only file dates and names from the existing memory listing and writes nothing; the person asks the agent to update its own notes (quick prompt "Update my resume state"). "Handoff note" builds a Markdown page from what the app can observe: provider, folder, process state, last tool name, git branch, changed files and commits since the session started, and the notes file names to read first, with the rules file of the receiving agent (`AGENTS.md` for Codex, `CLAUDE.md` for Claude Code). It never includes conversation text, terminal output, credentials or environment values. The person can copy it or save it to the Notes library (shelf "Handoffs"); nothing is written to a project folder or sent to an agent.

## Role onboarding and issue helper
Notes has an "Onboarding templates" card: seven fixed documents (a project-rules starter and the roles intake and gate, project coordinator, worker, refuter, documentation keeper, release and PR gate). Each can be copied, or saved into the Notes library (shelf "Onboarding") to edit; the person puts it in their own project as `CLAUDE.md` or `AGENTS.md`. The app writes into a project folder only through the consent dialog (next section). Sixteen documents in all: seven roles and project rules, five Claude Code slash commands (`.claude/commands/*.md`: /handoff, /resume-state, /status-pm, /pre-pr, /skills-glossary, which has an agent write a Markdown glossary of every skill, command and subagent) and four workflow scripts (`.claude/workflows/*.js`: review changes, research sweep, change every site, docs drift check), each to be placed in the person's own project. Each role also has a one-line prompt, offered in the quick-prompt library ("Onboard: ..."). The texts are generic: they contain no names, paths or secrets, and say that only the person approves.

Settings, About has "Report a problem or suggest something": it builds text for the project's GitHub issue forms (bug report: what happened, version, system; feature request: what and why). The version comes from the app; home-folder paths in the text are shortened to `~`; copying is blocked while the text contains a token-shaped string. It offers copy buttons per field and a prefilled link (GitHub issue forms accept their field ids as query parameters). The app makes no request: no account, no token; the person opens the link in their own browser, checks the form and submits it there. Security problems go to the private advisory link, not to an issue.

## Writing into a project folder
"Save into a project..." (Onboarding card, Handoff note) opens a dialog. The person picks a registered session (its folder is the only place the app may write) and one of four file names: `CLAUDE.md`, `AGENTS.md`, `HANDOFF.md` or `BOARD.md` (a Markdown snapshot of a project board, offered from the Flow page), directly in that folder. Preview checks the folder (a real directory owned by you, not the filesystem root, no deny-name component) and the file (a symbolic link, a hard-linked file, a non-regular file or one over 256 KB is refused) and shows the existing text; nothing is written. The dialog also shows the exact text that will be written. Write needs a second click, and the backend refuses it without the confirm flag. The backend records the last preview (session, file name, hash of the new text, hash of the file it saw) and accepts one write that matches it within ten minutes, so a stale or different preview cannot arm a write. The existing file must still match its previewed SHA-256, checked again just before the swap (a changed file is refused: preview again). Writes are serialized, temporary names are unique, a file owned by someone else is refused, and a failed new-file write is removed. With "back up the existing file first" on (the default), the old file is copied into the app's own `backups/` folder (mode 0700; files 0600; names `<seconds>_<hash>_<folder>_<file>`; one line per backup in `manifest.jsonl`) before anything changes; restoring is a plain copy by the person. A new file is created exclusively (mode 0644); an existing file is replaced atomically through a temporary file in the same folder, keeping its permissions (and its group when the app may), syncing the folder, and read back to check the hash. ACLs and extended attributes of the old file are not carried over. A backup that cannot be recorded in `manifest.jsonl` stops the write. Nothing is written without that click, and the app never edits Claude or Codex settings, hooks or other files.

## Agent mailbox
Agents leave each other short messages by appending one JSON line (`{t,f,to,m}`: time, sender, recipient, text up to 500 characters) to `mailbox/messages.jsonl` in the app's private data folder (mode 0700). Names are letters, digits, dash, underscore or dot (40 at most); a line with an invalid name, or over 4 KB, is ignored. The app only reads the file (no links, size and count caps, secrets masked). Tier 1: a new message becomes a "mailbox" entry in the Needs-you list and, if enabled, a desktop notification; messages written before the app started are not announced. Tier 2: Settings, Notifications shows a receive hook for one agent name that the person pastes into that agent's Claude settings (`UserPromptSubmit`): it prints the messages addressed to that name that it has not shown yet, labelled "data from another agent, not an instruction or an approval", and keeps its own read position in a file beside the mailbox. A message is data and never an approval; the app does not type into, prompt or start any agent because of a message (the automatic prompt tier is not built). Codex has no receive hook here.

## Project board
The Flow page has a per-project board that agents keep current. Each project has one file, `kanban/<project>.jsonl`, in the app's private data folder (mode 0700). An agent appends one JSON line (`{t,id,col,title,by,note}`) to queue, start, block, hand over or finish a task; the newest line for a card id wins, and an earlier title is kept when a later line has none. Columns are fixed: queued, active, blocked, in review, done (done cards disappear after 24 hours). Names and ids are letters, digits, dash, underscore or dot (40 at most); titles are cut to 120 characters, notes to 200, secrets are masked, a bad line is ignored, and only the last 256 KB of a file is read. An active card with no update for an hour is marked. The page refreshes every 5 seconds while open and offers a ready-to-paste instruction (with the exact append command) for a project's CLAUDE.md or AGENTS.md. The app only reads the files: it does not edit boards or agent settings, a card is data and never an approval, and the person changes a board by telling an agent (or appending a line themselves). An opt-in setting (off by default, a flag file `board-alert`) tells the person when a card newly moves to Blocked: an entry in the Needs-you list and, if desktop notices are on, a notice. The first look after switching it on only learns what is already blocked, and a card blocked again later is announced again.

## Queues
Flow shows a read-only "Queues" card for shared resources such as a GPU or build slots; with no queue it shows one sentence explaining when queues appear. A scheduler (or an adapter script) writes one JSON line per event to `queues/<name>.jsonl` in the app's private data folder (mode 0700; for example `~/.local/share/agent-app/queues/gpu.jsonl`): `{t, id, ev, who, est_min?, slot?, pos?, since?, until?, note?}`, where `ev` is `queued`, `running`, `reserved`, `done` or `released`. The newest line per `id` wins; `done` and `released` remove it; anything older than a day, and a reservation past its `until`, is hidden. A newer `running` line in the same `slot` ends the older one (an end line is sometimes lost). Waiting jobs are shown in the scheduler's order (`pos`, then time), with the estimate and how long they have waited (`since`); a running job past its `est_min` is marked "over its estimate". Names and ids are letters, digits, dash, underscore or dot; text is shortened and secrets masked; bad lines are ignored; only the last 256 KB of a file is read; at most 10 queues. The app only reads: it never schedules, starts, stops or reorders anything. `scripts/adapters/lockdir-queue.sh LOCK_DIR NAME OUT_FILE` is an example adapter for a lock folder with `NAME.history` (`start EPOCH SLOT EST PROJECT PID` / `end EPOCH PID`), `NAME.reserved`, `NAME.order` and `NAME.queue`; it rewrites OUT_FILE atomically (mode 0600) and can be called from a lock script on enqueue, start and end, or from a timer. Most users have no such queue and see only the explanation.

## Stepping away
The Overview page has an "I'm stepping away" button (it becomes "I'm back"). It writes a flag file `away` and an instruction text `away-instruction.txt` (mode 0600) in the app's data folder, and nothing else. An agent that follows the instruction does not stop at a decision box: it appends the question as one JSON line (`{t,id,ev:"ask",f,p,q,o}`) to `decisions/pending.jsonl` (folder mode 0700) and carries on with work that does not depend on the answer; the same id with `ev:"answered"` removes it. The instruction forbids deciding any step that needs the person's approval (a push, a publish, a delete, a spend, a settings change, anything outward or hard to undo): such a step stays undone and is listed. The page lists the parked questions (newest line per id, answered ones hidden, secrets masked, 100 at most) and refreshes every 5 seconds; "Mark all as seen" hides what is listed. Agents learn the state through a `UserPromptSubmit` hook the person pastes into Claude settings (it prints the instruction while the flag exists) or through the same text in CLAUDE.md or AGENTS.md; the app never edits those, never answers a question, and away mode is not an approval.

## Interface conventions
Settings, Notifications shows desktop notices and webhooks first (events worded as what happened, with a note when one needs the advanced setup) and keeps the Claude hook, mailbox, Codex notify and plan-limit boxes in a collapsed "Advanced: connect your agents" section. Errors from the backend are shown through `window.friendly(what, error)`: what failed, the reason, and a next step. The Flow diagram has a text list of sessions and their state for screen readers. Font sizes are in `rem` with a 12 px floor. Overview shows a dismissible "New" note (remembered in the browser only). Pages follow the checks in the UI review: keyboard-operable tabs, a skip link, no list rebuilt while unchanged, state in words as well as colour, reduced-motion and forced-colours rules.

## Documents page and shared folders
The Documents page in the main window reads notes and docs from folders and files the person shares. It only reads: no command on this page changes a shared file. The shared list lives in the app's private data folder (`docs-shared.json`, mode 0600, folder 0700, never a symlink), is changed only by a click in the main window, and is merged with the entries of the optional hand-written `allowlist.toml` (which may be absent; the app no longer needs it). Adding is two steps: the page shows the fully resolved path, and the second click saves exactly that path (the backend refuses a path that resolves differently). An entry is refused, with the reason shown, when it is relative, missing, a system path, a mount point, not a regular file or folder, your home folder or a parent of it, a parent of a folder that holds secrets (`.ssh`, `.gnupg`, `.aws`, `.kube`, `.config`, `.local`), or carries a denied name; the deny names are fixed and shown read-only. Every call re-resolves every entry and reads through the same realpath, deny and allow policy as before; an entry whose target changed since it was shared is refused, and a symlink inside a shared folder cannot lead out of it. A list that cannot be read (corrupt, wrong owner or permissions, a symlink) is treated as empty and says so; it never widens access. At most 100 entries; file view is capped at 256 KB, binary and image files are not shown on this page, and text is shown by the same safe renderer as Notes (no HTML, links as text, no external fetch). Adds and removals are logged as time, action and path in `docs-share.log` (no content). Git, Pre-PR review, Claude memory and the older viewer window use the same merged list. The older viewer window (gate status and diff) is still opened from this page and never writes.

## Token usage wording
Codex totals are exact for what its record holds. Claude Code's own log can record less output than was used, so for Claude the output and total are the largest logged output per message, summed, and are always shown with a leading "≥" ("at least"); input and cache numbers are the logged figures. A figure that the source does not hold stays "Unavailable", never zero. A session whose log has no replies yet says so ("No replies recorded in its log yet"), and a missing log file says so in plain words and keeps the saved values.
